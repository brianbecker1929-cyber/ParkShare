# BUG-005250 and BUG-005251: real spot layouts and future booking access

QA-only repair on PR #222 / c532987a6ebf5e05816bdc556349a9637ae38928. No database migration is required. Existing abandoned-checkout and extension repairs are retained; the blocked PR #221 migration is outside this candidate.

## Result

The ordinary Driver picker and its payment preview previously forced four physical bays. They now derive the layout from the Host's configured `spots`, retaining private bays and their original physical letters. Older listings without `spots` use their positive integer `spaces` capacity. Both paths support the existing Host-editor limit of eight bays. Invalid capacity does not invent a rentable bay. The same pure layout helper supplies rentable labels for the availability API; only `forRent === true` is rentable. Private Spot A does not renumber Spot B, E or H.

Grid rows/columns adapt to the physical count; dense layouts use smaller unselected icons. Existing selected vehicle rendering, orange border and label clearance are retained. Selection checks and the payment preview no longer cap the chosen index at D. Checkout still submits the original physical letter and uses existing server validation/atomic hold enforcement. No payment, refund, account, schema, grant or historical booking change is introduced.

The automatically opened spot dialog also now provides a clear Schedule for Later action, even when every current spot is occupied. It opens the existing property-local future date/time controls by switching to the future mode and closing the picker. The action does not choose a spot or start payment. Only a completed check for the selected future window can unlock a rentable bay; the current-time badge remains informational. Previous-window responses cannot unlock or overwrite a new selection. Host schedule closure, booked/held bays and missing/failed availability remain blocked.

This release addresses selection and payment previews. Booking-email layout BUG-005259 remains a separate ticket.

## Verification

They cover 1/2/3/4/6/8 bays; legacy/configured layouts; private holes with stable E/H indexes; invalid capacity; pending/held/closed availability; stale now/future replies; full-now to free-future selection and payment preview; the exact E/H Checkout POST label/date/vehicle; and four current confirmed bookings leaving a separate future slot available. The old actual App fails the one/six/eight-bay display regressions.

Existing tests are updated only to inject the real shared layout dependency and replace the obsolete assertion requiring a fixed A/B/C/D array. Full-suite, build, native CI and live QA source/readiness results are recorded in the PR. All test booking/account/Stripe data is synthetic. Real browser/Stripe acceptance remains for BetterQA; do not close tickets based only on automated tests or deployment.
