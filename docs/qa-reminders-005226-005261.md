# BUG-005226 / BUG-005261 — booking reminder delivery

The halfway and ending-soon handler existed, but `vercel.json` never scheduled it.
Register `/api/send-reminders` every minute with the existing `CRON_SECRET` bearer
protection. Both notifications go to the Driver, with the Host CC'd, using the
approved templates and QA links when `APP_URL` is the QA origin.

A confirmed, paid session becomes eligible at 50% elapsed and 15 minutes before
its canonical end. Payment age does not exclude future bookings. A late run
inside the ending window sends only the ending notification. Ended, cancelled,
unpaid and future sessions do not send. Normal delivery is on the first minute
scheduler tick after each threshold, plus provider/inbox processing time.

## Delivery safety

Apply `20261021104409_booking_reminder_delivery_005226_005261.sql` before deploying
this handler. The additive table stores the exact provider payload, accepted
message ID and a two-minute conditional lease. It is inaccessible to anonymous
and authenticated clients; only the service role can read or update it. The
provider idempotency key includes the database identity so QA and production
cannot collide. Retries preserve the initial payload. Acceptance is recorded
before the legacy booking timestamp, so a failed timestamp write is repaired
without sending again. An unknown delivery outcome can retry within 23 hours;
older uncertain outcomes require provider reconciliation to avoid a duplicate
after Resend's 24-hour key retention. Failed recipient or database lookups are
reported as failures, never successful sends.

A session is checked again immediately before sending. If an extension changes
the end after a delivery snapshot is created but before acceptance, the stale
snapshot is suppressed and requires reconciliation; an email displaying an old
end time must not be sent. Accepted reminders remain once per booking/kind.

The existing five-email regression verifies vehicle details, inline artwork,

1. Make a fresh one-hour paid booking using Stripe test mode. Confirm one
   halfway email around 30 minutes after its actual start, then one ending email
   around 45 minutes. Check Driver inbox and Host CC, including spam folders.
2. Check booking ID, vehicle, space, property-local end time and QA action links.
3. Repeat with Schedule for Later, including a listing outside Toronto. Timing
   follows the booking's actual start, not payment time.
4. Confirm no repeats on later minute ticks, and no reminders after cancellation

   expect only the ending reminder.

A successful cron invocation with zero due bookings validates scheduling and
access, but does not establish inbox delivery; BetterQA's fresh booking remains
the final email acceptance check. No production deployment is included.
