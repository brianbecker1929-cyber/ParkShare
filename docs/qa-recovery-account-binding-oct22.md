# Password recovery bound to its account — 22 October 2026

Code-identified defect; no assigned BetterQA ticket ID. A password-recovery editor remained open when the shared Supabase session signed out or changed accounts. Its updateUser call used whichever session the SDK read at submission, and it accepted a successful reply for any nonempty user ID. A stale reset form could therefore update a different signed-in account and show a misleading success screen. Two regressions reproduce stale secret retention/queued submission and acceptance of a different account's reply against the previous actual modal.

The PASSWORD_RECOVERY event now passes only its account ID to a fresh keyed editor. The editor retires its pending/queued handlers, clears both secrets, disables recovery inputs and shows fresh-link guidance on sign-out, a foreign/missing session or a changed target. A→B→A cannot revive the old editor; a fresh recovery event remounts it. Same-account token refresh is allowed. Close remains available after invalidation. Auth callbacks only invalidate local state; they never await SDK calls.

The recovery write takes a session snapshot, verifies that exact bearer with getUser(token), checks the current account again, then sends PUT /auth/v1/user with the verified captured token and the existing public key. That endpoint and User response are verified against Supabase Auth's official OpenAPI and the installed SDK. A different account appearing after preflight cannot change the request's principal. After the reply, verify both the returned account ID and current session before showing success. This path never calls shared updateUser, setSession or refreshSession, and never saves/broadcasts an obsolete response into shared storage. Completion restarts the existing read-only profile synchronizer instead of restoring a captured session.

Existing twelve-character validation, duplicate-submit lock, clear-on-success, request ownership, error handling, dialog replacement and normal sign-in/signup are retained. A request already sent may still change the original account's password; closing or invalidating UI does not undo that request. Transport/malformed-reply errors explain uncertainty and advise trying the new password before requesting another reset. No automatic password retry, recovery mail, new backend endpoint, admin privilege, auth setting, dependency or database migration is introduced. The SDK's getSession behavior (including its own refresh handling) is unchanged; no server-side session revocation guarantee is claimed.
