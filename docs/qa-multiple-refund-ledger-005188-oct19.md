# BetterQA BUG-005188 follow-up — multiple refund persistence

This follows the Host earnings repair. That read model already reads cumulative Stripe refunds, but the webhook previously rejected a second refund ID. This change reconciles each customer's successful/pending/failed/canceled refund into a service-only ledger, preserving the original single-refund reference and its individual amount/status. New cumulative amount fields are separate from those legacy fields.

## Behavior and protections

- All charge.refunded and refund.created/updated/failed deliveries use the same current-history reconciler. A signed connected-account event is required; current Stripe reads use that account. Validate payment/charge identity, mode, CAD amount and captured payment against the persisted booking or extension. Paginate the complete refund list; detect contradictory, incomplete and duplicate snapshots. No Stripe write or email is introduced.
- Read the parent revision BEFORE retrieving current Stripe history. A SECURITY INVOKER service-only RPC locks that parent, checks the revision, upserts every refund and updates totals in one transaction. Refund IDs/amounts/creation times/payment ownership are immutable. Duplicate deliveries do not add money twice. A stale snapshot or database failure returns HTTP 500 for Stripe retry; never acknowledge a failed write.
- Existing financial/cancellation/dispute writes advance the parent revision. The cancellation endpoint compares its original revision before saving a refund response, preventing a late response from overwriting webhook evidence. An already-submitted refund with a concurrent change returns a reconciliation message rather than claiming an overwritten booking.
- Only succeeded Refunds count as settled. Pending/requires_action amounts remain separate. Failed/canceled refunds remain recorded without contributing to settled totals. Individual refund totals must agree with the current Charge snapshot.
- Partial base refunds preserve the paid reservation and its availability hold. Verified legacy partially_refunded rows return to confirmed when reconciled; they are not globally backfilled. Full settlement marks the base booking refunded, while disputed/cancelled/refunded terminal states remain protected. A current Charge dispute is also preserved.
- Extension refunds retain their own payment ledger. They do not reduce booked hours, revoke parking time, or change the base booking's status. Existing support review for cancelling bookings with extensions remains.
- Driver transactions show cumulative refunded/pending amounts while retaining the original charge amount. Pending refund evidence alone does not label a reservation Cancellation pending; an actual cancellation request is required. Automatic cancellation of a partially refunded booking requires support review to avoid promising an incorrect full refund.
- Host fee/proceeds reporting retains the earlier verified read-only Stripe reconciliation, including actual application-fee refunds. This change does not set a new fee refund policy or issue refunds.

## Database rollout and verification

Apply the additive migration only to the active parkshare-qa database after disposable schema and native concurrency CI pass. It creates payment_refunds with RLS and no browser grants/policies; a service-only SECURITY INVOKER RPC; private revision triggers; and nullable cumulative totals/default-zero revisions. The transaction locks both parent tables briefly and compares before/after digests of every original column before commit; any mismatch rolls back the entire migration. There is no historical backfill, account change, actual charge/refund, event replay, or notification send. The migration filename is aligned to the service-tracked version before final QA deployment.

The full-schema rehearsal installs all earlier repairs first, then the photo cleanup and refund ledger. Synthetic transactions cover duplicate deliveries, multiple partial/full refunds, pending-to-failed lifecycle, incomplete/incorrect identity/mode snapshots, atomic rollback, stale revisions, cancellation/dispute protection, extension entitlement preservation and denied browser access. Native PostgreSQL additionally races two deliveries and a cancellation against a waiting webhook.

Review baseline Supabase advisories separately: existing mutable search_path functions, trigger-function execution grants, btree_gist placement and leaked-password configuration predate this migration. The new RPC has an explicit empty search_path, uses SECURITY INVOKER and denies browser execution. A no-policy INFO notice on the server-only ledger is intentional. Remediation references: https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable and https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable .

Complete the remaining refund and verify the base booking is refunded. Repeat duplicate and reordered deliveries, pending/failed refunds, wrong connected account/mode and injected database errors. Repeat multiple partial/full refunds against an extension; its parent hours and reservation must stay unchanged. Race cancellation against delivery and confirm no duplicate refund creation, lost references or overwritten totals. Test signed-in Driver/Host views and direct browser ledger/RPC denial. These genuine Stripe TEST and signed-in acceptance steps remain BetterQA's responsibility; automated mocks and disposable PostgreSQL are not a substitute for them.

Actual production and main remain unchanged. Do not mark the bug closed until BetterQA acceptance. No historical Stripe events are replayed automatically; earlier payments are reconciled only on a verified incoming delivery or a separately approved support review.
